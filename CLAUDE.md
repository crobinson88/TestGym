# CLAUDE.md — Gym Tracker

Personal phone-first gym-logging PWA for a single user (`charlie@theglassmarket.co`). Offline-first writes to IndexedDB, background sync to Supabase Postgres, Realtime push for multi-device.

## How to run

```
npm install
cp .env.example .env.local   # fill in URL + anon key
npm run dev                  # http://localhost:5173
npm run db:check             # prints sets row count, should be >= 1456
npm run build                # tsc + vite build
npm run test                 # unit (vitest)
npm run test:integration     # real Supabase round-trip; needs SUPABASE_TEST_ENV=1
```

## Stack

- Vite + React 18 + TypeScript + Tailwind + shadcn/ui
- Dexie (IndexedDB) — local store, every write hits this first
- `@supabase/supabase-js` — cloud store + auth (magic link) + Realtime
- `recharts` — history charts
- `vite-plugin-pwa` — installable PWA, service worker, iOS home-screen icons
- `vitest` — unit + integration tests
- Deploy: Vercel (`vercel.json` configures SPA rewrites + PWA headers)

- `french_attempts(id uuid pk, kind text check in (vocab, rules, conjug, listening, pronun, speak), total int check >= 0, correct int check (>= 0 and <= total), duration_ms int, details jsonb default '[]', started_at timestamptz, client_id uuid, user_id uuid default auth.uid(), created_at, updated_at, deleted_at)` — one row per completed French test (vocab, grammar-rules, verb-conjugation, listening, pronunciation-rules, or speaking). Same RLS / Realtime / offline-sync rules as `sets`. `details` is a `jsonb` array of `{questionId, prompt, correct}` per question so the stats view can surface most-missed items. The **study content is static client-side data, not a table**: `src/modules/french/data/` holds the top-2100 vocab list (`verbs.ts` = 200 most-common verbs + `words.ts` = 800 most-common non-verbs + `words2.ts` = ~1100 more words ranked ~801–1900, plus `activities.ts` = a themed leisure-activities / likes-and-dislikes lesson set — activity phrases, opinion expressions and model sentences whose `rank` is just lesson order — all combined in `vocab.ts`; the Dashboard tracks vocab "mastery" — words answered correctly >90% over ≥3 showings — as a % of the whole pool), `rules.ts` (multiple-choice grammar questions derived from the French Grammar Guide), `conjugations.ts` (present-tense tables for the core auxiliaries + top irregulars plus the opinion verbs — être, avoir, faire, aller, pouvoir, vouloir, devoir, venir, prendre, dire, voir, aimer, adorer, détester, préférer), and `pronunciation.ts` (multiple-choice questions on how French letters/combinations sound — vowels, nasal vowels, consonants, silent letters, liaison, accents — each with an optional `example` word). The French module (`/french`) generates a 10-question vocab, rules, conjugation, pronunciation, or speaking test (`quiz.ts`, pure + seeded-rng testable), scores it, and writes one `french_attempts` row; `stats.ts` aggregates accuracy/best/most-missed (the Dashboard's "French accuracy · last 8 weeks" chart plots weekly per-kind accuracy via `weeklyAccuracy`). Vocab tests take a `direction` (`fr2en`/`en2fr`/`mixed`, passed as `?dir=`). **Vocab word selection is spaced-repetition, not random**: `computeVocabSchedules` (in `stats.ts`) replays each word's showings from `french_attempts.details` into a Leitner box (correct answer → climb a box and widen the review gap via `REVIEW_INTERVALS_DAYS` = `[0,1,3,7,16,35]` days; any miss → box 0, due immediately), and `selectVocab` (`quiz.ts`) builds each test by **mixing reviews with new words**: it reserves a share of the test (`NEW_WORD_RATIO` = 0.3) for brand-new words and gives the rest to due/overdue reviews (most-lapsed = lowest box first, and within a box the most-recently-missed word leads — so a word you just got wrong jumps to the top of the queue and is retested in the very next test), then tops up any remaining slots with leftover reviews, not-yet-due words, and finally mastered ones — so wrong answers resurface at the optimal frequency until they stick, while new vocabulary keeps coming every session even when the review backlog could fill the whole test on its own (the reservation collapses to all-reviews only when there are no new words left to learn). The home screen shows the live "due for review" count (`dueForReview`); rules and conjugation tests stay uniform-random. The **listening test** (`kind='listening'`, question ids `listen:{fr}`) speaks each French word (or short phrase) via the Web Speech API (`speech.ts`, `fr-FR`; nothing is pre-recorded) and the learner reproduces what they heard by tapping words out of a shuffled **word bank** — the spoken words mixed with `LISTENING_ORDER_DISTRACTORS` (4) decoys — placing them in the order heard, so it grades on picking the right words **and** ordering them (`Question.sequence` = the spoken words in order; `checkOrder` grades the built list; `answer` is unused for these). The prompt text stays hidden until answered (`Question.audioText` drives the audio UI in `TestRunner`). Length (`?n=`, includes a single-word ear check), **words per round** (`?words=` → 1–4, `LISTENING_WORDS_PER_ROUND`/`clampWordsPerRound`), and playback speed (`?speed=` → normal/slow/very-slow, `LISTENING_SPEEDS`/`speedRate`) are chosen on the home screen. **The listening test only ever draws words the learner has already mastered in the written vocab tests** (`masteredVocab`/`useMasteredVocab` — the `isMastered` bar, >90% over ≥3 showings — so you only hear words you can read); the home screen disables the test until the first word is mastered. Single-word selection reuses `selectVocab` over the listening test's **own** Leitner schedule (`computeListeningSchedules`, kept independent of vocab so hearing and reading build separate review queues) and takes a study-mode (`?mode=` → mixed/review/new, `STUDY_MODES`/`clampStudyMode`): mixed = the default review+new blend, review = only words due, new = only never-heard words; it has its own stat card, recent-test entries, and accuracy line. With `words=1` each round speaks one word (`listen:{fr}`, the canonical per-word SR drill — the bank is that word plus decoys and the "order" is trivially one word). With `words>1` each round is a **natural French sentence generated server-side** from the learner's mastered words (`POST /api/french-chat` with `action:"sentences"` — the chat endpoint doubles as the sentence generator to stay within Vercel's function budget — → Claude `claude-sonnet-4-6` with a `zodOutputFormat` schema of `{fr, en, words[]}`; the client `fetchSentences` + `makeSentenceQuestion` turn each into an ordering question) — the sentence is spoken and the learner rebuilds it word-by-word in order from the bank (spoken words + decoys drawn from mastered vocab). These sentence rounds are fetched async in `TestRunner` (with a generating + retry-on-error state, the mode selector hidden since selection is by the model) and carry a `phrase:{…}` id prefix so — since `listenKeyFromQuestionId` only recognises `listen:` ids — they stay out of the per-word schedule (connected-speech comprehension practice, not the per-word drill). Conjugation tests cover the **present tense** and the **futur proche** ("going to …", derived at quiz time as aller-present + infinitive — not stored); question ids are `conjug:{infinitive}:{tense}:{person}`. The **pronunciation test** (`kind='pronun'`, `?n=`, uniform-random over `PRON_QUESTIONS`) is multiple-choice like the rules test — question ids are the static `PronQuestion.id` slugs — but each question can carry an `example` French word the learner plays via TTS (`Question.example`, a "hear it" aid that keeps the prompt **visible**, unlike `audioText` which hides it for the ear-only listening test). The **speaking test** (`kind='speak'`, `?n=`, question ids `speak:{infinitive}:{tense}:{person}`, uniform-random over verb×tense×person like conjug) drills **pronouncing** conjugations: it shows the form (single clean subject pronoun, je→j' elided, present + futur proche), the learner says it aloud, taps to hear the model pronunciation (`Question.example` via TTS), then **self-assesses** Got-it/Missed — `choices` is empty and `answer` unused; grading is self-reported (no browser speech-recognition, since iOS Safari/PWA doesn't support it), and the self-mark is what's saved to `details`/stats. Both new kinds get stat cards, most-missed entries, and a weekly-accuracy line like the others, but stay uniform-random (no spaced-repetition schedule). `/french/rules` renders a static reference guide (`data/guide.ts`). `/french/chat` is a roleplay conversation partner: `POST /api/french-chat` sends a scenario + the conversation so far to Claude (`claude-sonnet-4-6`) and returns the next French line (beginner-level, with a short `✏️` correction when the learner slips); nothing is persisted server-side, same auth gate as the other AI endpoints.

One **live row per day**: `smoked` is `true` (smoking day) or `false` (smoke-free), and `cigarettes` is how many were smoked that day — `null` when the count is unknown (day marked "Smoked" from the Today toggle without a number), `0` on a smoke-free day; **no live row = the day is unmarked**. There's no DB unique on `log_date` — dedup is client-side (`useSmokingForDate` and the mutations resolve the newest live row, matching how `stocks` dedups). The Today card shows a two-button toggle (Smoke-free / Smoked); tapping the active choice again clears the mark. `setSmoked(date, true|false|null)` (`sync/mutations.ts`) updates the day's live row (smoke-free → 0 cigarettes; a smoking day carries any positive count already entered, else stays unknown), creates it, or soft-deletes every live row for the day when passed `null`. `setCigaretteCount(date, n|null)` sets the count (n > 0 marks the day smoked, 0 marks it smoke-free, `null` clears the mark). The Stats page (`Dashboard.tsx`) has a **Smoking** section: a month calendar (`SmokingCalendar`, Monday-first, prev/next month nav) colouring each day green (smoke-free), red (smoked, showing the count), or neutral (no data), plus the month's total cigarettes; **tapping a day opens an inline editor** (`SmokingDayEditor`, ± stepper + numeric input) to log/edit the cigarette count. Fed by the `useSmokingLogMap` date→`{smoked, cigarettes}` map.
- `workstreams(id uuid pk, title text not null, type text check in (code_cli, web_chat, email_task), status text check in (in_progress, waiting_input, completed, failed) default 'in_progress', source_id text, last_action text, metadata jsonb not null default '{}', client_id uuid, user_id uuid default auth.uid(), created_at, updated_at, deleted_at)` — the **Workstream Command Center** (`/workstreams`, `src/modules/workstreams/`), a desktop-only live table of every Claude workstream in flight. Same RLS + soft-delete + Realtime rules as `sets`, but **deliberately NOT in the Dexie offline-sync set** (`SYNC_TABLES`) — the rows describe processes on *other* machines, so an offline copy is meaningless and CLI hooks fire on every turn, which would push pure churn to the phone. The view reads Supabase directly (`api.ts`) and holds one Realtime channel only while mounted; the header badge (`useWorkstreamAlert`) fetches two counts and is skipped entirely off desktop. `source_id` is the terminal session id / Gmail thread id, null for hand-typed rows; a **partial unique index on `(type, source_id) where deleted_at is null`** keeps one live row per source. Writes from outside the browser go through the `workstream_upsert(p_type, p_source_id, p_title, p_status, p_last_action, p_metadata)` RPC (nulls leave the stored value alone, `metadata` is merged not replaced) — an RPC rather than a PostgREST upsert because `ON CONFLICT` can't infer a partial unique index. Three sources feed it: (1) **Claude Code CLI** — `scripts/workstream-hook.sh` wired into `~/.claude/settings.json` on SessionStart/Notification/Stop/SessionEnd, posting straight to PostgREST with the laptop's service-role key (no Vercel function: api/ is at the Hobby 12-function cap, and a per-turn hook shouldn't pay a cold start); it detaches and always exits 0 so it can never fail a CLI turn. (2) **Email triage** — the "Triage email" button → `POST /api/fireflies-import` with `action:"workstream-triage"` (multiplexed onto the meeting-import endpoint for the same budget reason french-chat doubles as the sentence generator) → `api/_workstreams.ts` pulls recent unread Gmail via the **existing calendar service account** extended with `gmail.readonly` (`getGoogleAccessToken(scope)` in `_gcal.ts`), Claude `claude-sonnet-4-6` + `zodOutputFormat` picks the genuinely actionable ones, one row per thread. On-demand only — Hobby crons fire once a day, useless for a live board. Nothing is marked read; nothing is persisted server-side. (3) **Web/Cowork chats** — added by hand ("+ Web session"), since no public webhook exists for them. Pure metrics/filter/sort/staleness math lives in `compute.ts` (`summaryMetrics`, `visibleWorkstreams`, `isStale` — 30-min window so a session killed without a Stop greys out rather than lying, `relativeTime`) and is tested.
- Model builder: `/shares/stock/:ticker/model` (`ModelBuilder` page). Revenue and one profit line are forecast **per business segment** (name, base revenue, growth, margin) and summed to a consolidated P&L. The profit line's **basis is chosen once for the whole model** — Gross Profit, EBIT, or EBITDA — since companies disclose different lines; everything below it (tax, D&A, capex, working capital, balance sheet) stays consolidated (D&A is always an input — it bridges EBITDA↔EBIT and is the cash-flow add-back). A deterministic client-side engine (`src/modules/shares/model/engine.ts`) builds a fully-linked 3-statement model (income statement / balance sheet / cash flow, equity is the opening plug so it always ties out) and renders a live preview. `model/excel.ts` exports a **live formula** `.xlsx` via `exceljs` (assumptions are editable input cells, statements are real formulas that recalc in Excel) — `exceljs` is dynamically imported so it only loads on generate. ### Important schema rules

- **Never write to `volume`** — Postgres maintains it from `weight * reps`.
- **Always set `id` client-side** (uuid v4) so offline writes have a stable identity for sync.
- **Soft delete only** — set `deleted_at`, never `DELETE`. Filter `deleted_at is null` on read.
- **`updated_at` is the LWW clock** — set on every local mutation (client clock is fine; single user).
- **`user_id` defaults to `auth.uid()`** server-side. The 1,456 historicals have `user_id = NULL` and stay that way; RLS gates on JWT email, not user_id.

## Auth

((auth.jwt() ->> 'email') = 'charlie@theglassmarket.co')

Session persists indefinitely (`persistSession: true`). Sign in once per device.

## Sync model

1. UI mutation → `db.sets.put(row)` with `sync_status='pending'`, `updated_at=now`. Returns instantly.
2. Outbox worker drains pending rows to Supabase whenever `navigator.onLine`. On success → `sync_status='synced'`. On failure → exponential backoff.
3. Realtime subscription on `sets`, `exercises`, `categories` upserts incoming rows into Dexie if `remote.updated_at > local.updated_at` (LWW). Otherwise insert into `conflicts` and keep local.
4. Soft deletes propagate via `deleted_at`.

If the spreadsheet gains rows the app didn't generate, run `scripts/import.py` to call the `public.bulk_load_sets(payload jsonb)` RPC. Idempotent on `(exercise_id, performed_at, weight, reps)` — re-running with the same rows is safe.
